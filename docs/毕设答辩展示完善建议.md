# 毕设答辩展示完善建议

在现有可运行 Demo 基础上，为方便答辩时展示和回答老师提问，建议从以下几方面完善。

---

## 一、演示流程与文档（优先）

### 1. 固定一套「从零到可玩」的演示步骤

- **目的**：答辩时能稳定复现「文本 → 事件图 → 分支 → Ren'Py 游戏」全流程，避免现场卡壳。
- **建议**：
  - 在 `README.md` 最前面增加 **「毕设 Demo 快速开始」** 小节，用 3～5 步写清：
    1. 环境准备（Python 版本、`pip install -r requirements.txt`、Neo4j 安装/启动、`.env` 配置）。
    2. 若已有 `out/` 部分产物：直接运行哪几条命令可生成/更新游戏（如 `import_assets.py` → `generate_renpy_scripts` 或对应 CLI）。
    3. 如何启动 Ren'Py 并进入游戏（例如：用 Ren'Py 启动器打开 `wangfo` 目录并运行）。
  - 在 `scripts/README.md` 或单独写 **`docs/DEMO_SCRIPT.md`**：按顺序列出「完整从原文到游戏」的每条命令（含 `src.cli` 与 `import_assets.py`），并注明每步的输入/输出文件，方便你照着讲、也方便老师事后复现。

### 2. 演示前检查清单

- 单独一个 **`docs/答辩前检查.md`** 或放在 README 里，包含：
  - Neo4j 已启动、端口 7687 可连。
  - `.env` 中 API Key 有效（若用 DeepSeek/Gemini）。
  - 项目根下存在 `王佛脱险记.txt`（或你实际用的源文本）。
  - 已解压的 `Japanese Music Pack`、豆包场景图等资源在约定位置（若演示需要 BGM/背景）。
  - 已运行过 `import_assets.py` 和脚本生成，`wangfo/game` 下剧本与资源完整。
  - Ren'Py 版本建议（如 8.x），避免版本不兼容。

---

## 二、答辩用说明材料

### 3. 创新点与贡献（1～2 页）

- **目的**：讲清「和现有工作的区别」以及「你做了什么」。
- **建议**：在 `docs/` 下写 **`创新点与贡献.md`**（或放进论文/开题），简要列出：
  - 从小说文本到事件图谱、再到多分支剧情与可玩 Demo 的**端到端流程**；
  - **状态管理 + 分支生成**（如 LangGraph、决策点、结局候选）在剧情一致性上的作用；
  - **与纯手工写分支、或纯模板生成的对比**（可一句话概括）。

### 4. 系统架构与数据流（老师常问）

- 你已有 `system-architecture.md` 和 README 里的数据流，答辩时可直接用。
- **建议**：
  - 在 README 或 `docs/` 中**明确贴一张「从原文到游戏」的流程图**（可手绘拍照或 Mermaid），并标注：事件提取 → Neo4j → 人物/状态 → 主线/支线 → 路径 JSON → Ren'Py 脚本 → 游戏。
  - 若老师问「某一步的输出是什么」，能快速指出对应 `out/` 下的文件（如 `extract_chain.json`、`all_paths/`、`enhanced_paths/`）。

### 5. 已知限制与未来工作

- **目的**：老师问「有什么不足 / 还能怎么改进」时，有现成答案，显得思考充分。
- **建议**：在 `docs/` 写 **`已知限制与未来工作.md`**，简短列出例如：
  - 依赖 LLM API，存在延迟与稳定性问题；长文本下的成本与速度权衡。
  - 分支数量、结局数量受限于当前决策点与策略。
  - 当前 Ren'Py Demo 的 UI/演出可进一步优化（立绘、演出、存档说明等）。
  - 可扩展方向：更多结局、更细粒度状态、多轮对话、难度/风格控制等。

## 三、工程与可复现性

### 6. 环境与配置

- **`.env.example`**：列出所有用到的环境变量（如 `DEEPSEEK_API_KEY`、`NEO4J_URI`、`NEO4J_USER`、`NEO4J_PASSWORD` 等），并注明「复制为 `.env` 后填写」，避免答辩现场缺配置。
- **`requirements.txt`**：确认包含演示所需的全部依赖，并注明 **Python 版本**（如 `# Python 3.10+`）。
- **README**：在「环境要求」中写清：Python 3.x、Neo4j 4.x/5.x、Ren'Py 8.x（若需）。

### 7. 一键或最少命令跑通 Demo（可选）

- 若时间允许，可加一个 **`scripts/run_demo.py`** 或 **`run_demo.bat` / `run_demo.sh`**：
  - 检查 Neo4j、`.env`、必要文件是否存在；
  - 按顺序调用：`import_assets` → 生成脚本（或你当前最少步骤）→ 打印「请用 Ren'Py 打开 wangfo 并运行」。
- 不要求全自动从「裸文本」跑到游戏，可假设 `out/` 里已有部分结果，只做「从现有数据到可玩包」的自动化，减少现场操作步骤。

## 四、展示时的注意点

### 8. Demo 展示顺序建议

1. **先播/先跑游戏**：用 1～2 分钟展示一条主线 + 一个分支选择 + 一个结局，让老师建立直观印象。
2. **再讲流程**：对照架构图/数据流，说明「刚才看到的剧情是从哪一步来的」（事件图 → 决策点 → 路径 → 剧本）。
3. **可选**：用 Neo4j 浏览器或你已有的可视化，快速展示事件/人物/关系，说明「知识图谱如何支撑分支与状态」。

### 9. 网络与 API 依赖

- 若答辩现场网络不稳或不能访问外网：
  - 提前用**录屏**录好「从运行命令到进入游戏」的完整过程，并准备好**离线可用的 Neo4j 数据**（导出/备份）。
  - 在文档中注明「演示依赖 DeepSeek API，建议提前测试网络」。

### 10. 论文/开题与代码的对应

- 若论文里有「系统实现」或「关键算法」小节，在文档里**注明对应代码位置**（如：分支生成逻辑见 `src/branch/generation/path_generation_functions.py`），方便老师追问时快速打开。

---

## 五、建议优先级小结

| 优先级 | 事项 | 说明 |
|--------|------|------|
| 高 | README 增加「毕设 Demo 快速开始」 | 3～5 步到可玩，减少现场试错 |
| 高 | 固定演示命令顺序文档（DEMO_SCRIPT） | 你按顺序讲，老师可复现 |
| 高 | 答辩前检查清单 | 环境、API、资源、Neo4j、Ren'Py |
| 中 | 创新点与贡献 1～2 页 | 便于讲「做了什么、和别人的区别」 |
| 中 | 已知限制与未来工作 | 应对「有什么不足/如何改进」 |
| 中 | .env.example + requirements 说明 | 提高可复现性 |
| 低 | 一键/最少命令 Demo 脚本 | 有时间可做，提升体验 |
| 低 | 论文与代码对应说明 | 方便老师深挖实现 |

按上面顺序逐项完善，答辩时展示会更稳、回答也会更有条理。你当前已有可运行 Demo 和较完整的 README/数据流文档，重点补「演示步骤」和「检查清单」即可明显提升答辩时的顺畅度。

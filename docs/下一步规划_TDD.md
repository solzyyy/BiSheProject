# 下一步规划：测试驱动开发与流水线管理

本文档用于定义本项目下一阶段“做什么”，不再重复 TDD 的通用工作规则。TDD 执行规则、优先级和任务级完成定义由 `.cursor/skills/tdd_pipeline/SKILL.md` 统一管理。

本规划面向当前项目的实际情况制定：系统核心功能已经基本完成，但缺少统一的流水线管理办法、运行状态记录、分步骤验证机制，以及成体系的测试代码。

---

## 一、总目标

将当前项目从“由多个 CLI 命令组成的功能集合”推进为“可管理、可验证、可续跑、可复现”的生成系统。

下一阶段的目标不是“再增加几个功能”，而是达到以下状态：

1. 能用统一方式描述一次完整运行。
2. 能知道流水线当前运行到哪一步。
3. 能在中断后恢复运行，而不是从头猜测。
4. 能对每个关键阶段的输出进行自动验证。
5. 新增或修改业务逻辑前，先有对应测试，再实现代码。

---

## 二、第一阶段：流水线配置层

### 2.1 目标

解决“每个命令都有参数、很难统一管理”的问题。

### 2.2 要做什么

设计统一的流水线配置文件，例如：

- `configs/demo_wangfo.json`
- `configs/longtext_validation.json`

配置文件至少应包含以下内容：

1. 全局参数
   - `run_id`
   - `input_text`
   - `output_root`
   - `validate_after_each_step`
   - `resume_from`

2. 步骤开关
   - 哪些步骤启用
   - 哪些步骤跳过

3. 步骤参数
   - 某一步专属参数，如 `generate-all-paths` 的 `canonical`
   - 某一步输入输出目录
   - 是否清库、是否启用某种高级选项

### 2.3 运行配置与环境配置分离

配置层必须区分以下两类信息：

1. 运行配置
   - 适合写入 `configs/*.json`
   - 例如输入文本、输出目录、步骤开关、步骤参数

2. 环境配置
   - 必须放在 `.env`
   - 例如 API Keys、Neo4j 密码、其他敏感信息

禁止将敏感信息直接写入 `configs/*.json`。

### 2.4 先写什么测试

在写配置加载逻辑前，先写以下测试：

1. 配置文件可正确读取
2. 缺少必填字段时会报错
3. 未声明的步骤不会被错误执行
4. 默认参数会被正确补全
5. 步骤级参数能覆盖全局默认值
6. 配置文件中若出现敏感字段，会被拒绝或给出明确警告

### 2.5 实现验收标准

- 能加载一个配置文件并解析成统一结构
- 能明确输出当前 `run_id`、输入文本、启用步骤列表
- 配置错误时给出清晰报错
- 敏感信息不进入版本化配置文件

## 三、第二阶段：运行状态管理

### 3.1 目标

解决“我现在跑到哪一步了”“失败后怎么继续”的问题。

### 3.2 要做什么

为每次运行生成状态文件，例如：

- `runs/<run_id>/state.json`

建议记录字段：

- `run_id`
- `input_text`
- `started_at`
- `finished_at`
- `current_step`
- `steps.<step_name>.status`
- `steps.<step_name>.started_at`
- `steps.<step_name>.finished_at`
- `steps.<step_name>.output_paths`
- `steps.<step_name>.validation_status`
- `steps.<step_name>.error`

### 3.3 建议增加的运行元数据

为了提高可复现性，状态文件还应尽量记录以下元数据：

- `model_name`
- `prompt_version`
- `temperature`
- 可选：`provider`
- 可选：`max_tokens`

这些字段的意义在于：后续论文、答辩和实验结果需要说明“这一轮结果是在什么模型和提示词版本下得到的”。

### 3.4 先写什么测试

在写状态管理逻辑前，先写以下测试：

1. 初始化运行时会创建状态文件
2. 每步开始时状态会更新为 `running`
3. 成功结束后状态会更新为 `passed`
4. 失败时会记录 `failed` 与错误信息
5. 恢复运行时能从最后失败或未完成步骤继续
6. 元数据字段会被正确写入和读取

### 3.5 实现验收标准

- 任意时刻都能从状态文件看出当前运行进度
- 中途失败后可根据状态文件恢复
- 状态文件是 JSON，可被后续报告生成脚本读取
- 关键元数据足以支持论文中的实验可复现性描述

## 四、第三阶段：统一流水线入口

### 4.1 目标

让系统不再只是“很多散命令”，而是“可编排的流水线”。

### 4.2 要做什么

建议新增统一命令，例如：

- `run-pipeline`
- `resume-pipeline`
- `validate-run`
- `summarize-run`

说明：

- `run-pipeline`：按配置文件顺序执行各步骤
- `resume-pipeline`：按状态文件恢复
- `validate-run`：统一校验本轮运行产物
- `summarize-run`：生成摘要报告
- `evaluate-solution`：对“小说抽取 -> 文游脚本”做子问题量化评估（覆盖率/交互密度/分支支撑/资产支撑）

### 4.3 先写什么测试

在写执行入口前，先写以下测试：

1. `run-pipeline` 会按步骤顺序调度
2. 禁用的步骤不会执行
3. 某一步失败时后续步骤不会继续
4. 开启 `validate_after_each_step` 时会触发对应验证
5. `resume-pipeline` 会跳过已完成步骤

### 4.4 实现验收标准

- 能通过配置文件启动一次完整运行
- 能在日志或状态中看到每一步是否执行成功
- 能在失败后恢复，而不需要人工重新判断

## 五、第四阶段：验证函数

### 5.1 目标

将“靠人工看文件”升级为“自动给出通过/失败结果”。

### 5.2 建议优先补的验证函数

第一优先级：

1. `validate_renpy_game()`
2. `validate_extract_chain()`

第二优先级：

3. `validate_entities()`
4. `validate_logical_consistency()`

后续逐步补齐：

5. `validate_state_baseline()`
6. `validate_canonical_branch()`
7. `validate_branches()`
8. `validate_all_paths_completed()`
9. `validate_enhanced_paths()`

说明：

- 第一优先级解决“能不能展示”和“基础数据对不对”
- 第二优先级解决“内容之间是否能对得上”
- 其余部分按实际出错频率和工程压力逐步补

### 5.3 每类验证至少检查什么

#### 事件链

- 文件存在
- JSON 可解析
- 非空
- 每条事件有 `event_id` 或等价字段

#### 实体表

- 文件存在
- JSON 可解析
- `canonical_name` 唯一
- 别名无跨实体冲突

#### 主线与分支

- 文件存在
- 路径非空
- 关键字段齐全
- 能对应到预期的分支或主线结构

#### 逻辑一致性

- 路径中引用的实体都能在实体表中找到
- 主线或分支中引用的事件能在事件链中找到
- 关键中间产物之间的引用关系不悬空

#### 最终游戏工程

- `script.rpy` 存在
- 存在 `label start`
- 存在 `jump canonical_path`
- 路径和结局脚本目录存在

### 5.4 关于 Token 与成本的记录

建议增加 Token 或成本相关的记录能力，但暂不作为第一批核心 validator。更适合将其作为：

- `collect_token_usage()`
- `record_token_usage()`

这类指标采集函数，而不是严格的布尔校验函数。

### 5.5 先写什么测试

在每个验证函数实现前，先写对应测试输入：

1. 正常样例：应该通过
2. 文件缺失样例：应该失败
3. JSON 损坏样例：应该失败
4. 字段缺失样例：应该失败
5. 交叉引用错误样例：应该失败

### 5.6 实现验收标准

- 每个验证函数返回统一结构，如 `passed / detail / errors`
- 可被 `validate-run` 和论文测试章节复用
- 逻辑一致性校验能发现至少一类跨文件引用问题

## 六、第五阶段：最小测试集

### 6.1 目标

让答辩和论文中的测试不仅“说得出来”，而且“真的可执行”。

### 6.2 最小测试集

#### 测试 1：全链路烟雾测试

目的：

- 验证主测试文本可以完整生成最终游戏

数据：

- `王佛脱险记.txt`

通过标准：

- 核心步骤无中断
- `wangfo/game/` 成功生成
- 最终游戏可启动

#### 测试 2：中间产物结构校验

目的：

- 验证关键中间结果存在且结构正确

通过标准：

- 所有关键 JSON 和目录通过验证函数

#### 测试 3：Ren'Py 可运行性验证

目的：

- 验证最终 Demo 可展示

通过标准：

- 游戏可启动
- 主线可进入
- 至少 1 个分支可跳转到结局

#### 测试 4：第二文本轻量验证

目的：

- 验证系统不是只适配《王佛脱险记》

数据：

- `docs/validation_samples/马尔戈的微笑.txt`

通过标准：

- 可提取结构化事件
- 可生成实体结果
- 可生成基础状态结果

## 七、第六阶段：单元测试

### 7.1 目标

为后续重构提供最基础的安全网。

### 7.2 适合优先补单元测试的对象

1. 配置解析函数
2. 运行状态读写函数
3. 路径拼接和输出目录管理函数
4. 别名冲突检测函数
5. 事件 ID 排序或格式化函数
6. 纯 JSON 验证辅助函数

### 7.3 暂时不优先的对象

以下内容暂时不作为第一批单元测试重点：

- 强依赖外部 LLM API 的核心生成逻辑
- 强依赖 Neo4j 在线实例的复杂集成逻辑
- 需要大量 Mock 才能跑通的复杂工作流节点

原因：

- 当前阶段应优先建立“最小可运行、最小可验证”的工程闭环

---

## 八、当前最值得立刻开始的

如果只做一件事，优先做：

**设计并实现“流水线配置文件 + 运行状态文件”的测试与最小实现。**

原因：

- 这是后续统一管理参数和步骤的基础
- 这是恢复运行和生成报告的基础
- 也是把当前 CLI 从“命令集合”升级为“流水线系统”的第一步

---

## 九、阶段性完成判据

当以下条件全部满足时，说明下一阶段的 TDD 基础已经建立：

1. 新业务逻辑实现前，已经有对应测试。
2. 可以用配置文件描述一次流水线运行。
3. 可以从状态文件看出运行进度。
4. 可以统一执行验证并输出通过/失败结果。
5. 至少具备 4 项可执行的最小测试集。
6. 论文第 5 章中的测试描述，能够对应到实际脚本和结果文件。

达到以上状态后，再继续扩展业务逻辑，整体开发会清晰很多，也更适合答辩与论文写作。

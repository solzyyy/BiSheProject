# 系统技术方案说明

> 本文档详细描述系统各阶段的技术方案、算法设计与数据流转，可作为论文"系统设计与实现"章节的参考材料。

---

## 一、事件图谱构建

从原始文学文本中提取结构化事件信息，构建事件知识图谱。

**处理流程**：

1. **文本分段**：使用 `TextProcessor.split_text_to_paragraphs()` 将全文按自然段落分割，每个段落作为一个提取单元
2. **事件提取**：对每个段落调用 LLM（通过 `AsyncLLMClient.invoke(return_json=True)`），从中提取结构化事件，每个事件包含：
   - `event_id`：事件唯一标识（E1, E2, ...）
   - `scene_description`：场景描述
   - `source_text`：原文引用
   - `dialogue`：对话列表（speaker, text, tone）
   - `characters`：涉及人物
   - `actions`：行动描述
3. **关系提取**：对相邻事件对调用 LLM，识别事件间的因果关系（caused_by）和时间顺序（followed_by），生成有向关系边
4. **数据合并与导入**：将事件列表和关系列表合并，导入 Neo4j 图数据库，创建 Event 节点和关系边

**输入**：原始文本文件（王佛脱险记.txt）

**输出**：
- `out/extract_chain.json` — 结构化事件列表
- `out/extract_relations.json` — 事件间关系列表
- Neo4j 数据库中的 Event 节点和关系边

---

## 二、人物实体识别与规范化

基于事件图谱识别并规范化文本中出现的所有人物实体。

**处理流程**：

1. **Mention 提取**：遍历所有事件，使用 LLM 从事件的 `scene_description`、`dialogue`、`source_text` 中识别人物提及（Mention），记录每个人物在哪些事件中被提及及其角色（施事者 / 受事者 / 旁观者）
2. **实体消歧与别名映射**：使用 LLM 对所有 Mention 进行聚类，将同一人物的不同称呼（如"皇帝""天子""陛下"）归并到同一规范实体下。输出的实体表包含规范名称（canonical_name）和所有别名（aliases）的映射关系

**关键算法**：实体消歧采用两阶段策略——先通过 LLM 识别候选别名对，再通过上下文验证确认。Ren'Py 脚本生成阶段也利用实体表将对话中的不同称呼统一为同一角色变量。

**输入**：`out/extract_chain.json`（事件列表）

**输出**：
- `out/mentions.json` — 人物提及表（事件级别的人物出现记录）
- `out/entities.json` — 实体表（规范名称 + 别名映射）

---

## 三、状态变化提取

从事件图谱中提取三类状态变化，为后续状态管理和分支生成提供数据基础。

### 3.1 人物内在状态（character_states）

通过 Mention 表定位人物相关事件，结合实体表进行别名映射，调用 LLM 分析事件中人物的内在维度变化。提取的维度包括：情绪状态（emotional_state）、动机（motivation）、世界观（worldview）、认知状态（cognitive_state）等。每条状态变化记录包含 `target`（目标人物）、`dimension`（维度名）、`old_value`、`new_value`、`trigger`（触发事件）。

### 3.2 世界/物品状态（world_states）

直接从事件中识别场景、环境、物品等外部世界的变化。维度包括：场景状态（scene_state）、环境状态（environment_state）、物品存在（item_existence）、社会状态（social_state）等。

### 3.3 人物关系状态（relationship_states）

识别事件中人物对之间的关系维度变化。维度包括：情感状态（emotional_state）、权力动态（power_dynamic）、连接强度（connection_strength）、信任水平（trust_level）等。

**输入**：事件列表、Mention 表、实体表

**输出**：
- `out/character_states.json` — 人物内在状态变化列表
- `out/world_states.json` — 世界/物品状态变化列表
- `out/relationship_states.json` — 关系状态变化列表

---

## 四、人物画像聚合

整合事件数据、状态变化数据和人物提及数据，为每个人物生成完整的动态画像。

**关键算法**：

1. **行动词提取**：从事件描述中使用 LLM 提取人物的行动词（动词短语）
2. **TF-IDF 计算**：统计每个行动词在各人物中的频率，计算 TF-IDF 值以识别角色的典型行为
3. **PMI（点互信息）计算**：计算行动词与人物之间的共现关联度，识别每个人物独有的行为模式。PMI 公式为 `PMI(word, character) = log2(P(word, character) / (P(word) * P(character)))`
4. **画像聚合**：综合事件参与统计、行动模式、独有行为、相关状态变化，生成每个人物的完整动态画像

**输入**：事件列表、人物状态、关系状态、实体表、Mention 表

**输出**：`out/character_profiles.json` — 人物画像列表

---

## 五、静态人设聚合

基于动态人物画像，通过 LLM 提取人物的五个核心静态属性：

| 属性 | 说明 | 示例 |
|------|------|------|
| role | 叙事角色定位 | 主角、对手、导师 |
| social_position | 社会位置 | 宫廷画师、流浪僧人 |
| disposition | 性格倾向 | 坚忍淡泊、权力欲强 |
| worldview | 世界观 | 以艺术为生命意义 |
| persona_summary | 综合人设摘要 | 一段完整的人物定位描述 |

每个属性通过独立的 LLM 调用提取，最后由 `generate_persona_summary()` 生成综合摘要。静态人设在主线生成阶段用于约束 LLM 的决策，确保角色行为符合人物设定。

**输入**：`out/character_profiles.json`（人物画像）

**输出**：`out/character_personas.json`（静态人设列表）

---

## 六、状态基线初始化

扫描所有已提取的状态变化，按 `target_type`（character / world / relationship）和 `dimension` 进行聚类，识别出系统中所有可能的状态维度。为每个维度设置初始值（通常为 neutral / unknown / 0），作为运行时状态变量的起点。

状态基线是主线生成和分支生成的起始状态，所有后续的状态更新都在此基础上进行。

**输入**：三类状态变化列表

**输出**：`out/state_baseline.json`（包含按目标类型分类的所有维度集合及初始值）

---

## 七、数据持久化（Neo4j）

将实体数据和状态变化数据导入 Neo4j 图数据库，建立与事件节点的关联关系。Neo4j 中的数据模型：

```
(Event)-[:HAS_STATE_CHANGE]->(StateChange)
(Event)-[:MENTIONS]->(Entity)
(Event)-[:FOLLOWED_BY]->(Event)
(Event)-[:CAUSED_BY]->(Event)
```

为 StateChange 节点建立多维索引（target_type、dimension、event_id），支持高效的状态查询。在主线生成阶段，`StateApplier` 通过 Neo4j 查询获取与当前事件关联的所有状态变化。

---

## 八、主线生成（Canonical Branch）

从第一个事件开始，逐步遍历事件知识图谱中的所有事件，应用状态变化，生成主线记录。主线代表"无人干预下真实发生过的历史"，是后续分支生成的参照基准。

**核心流程**：

```
for each event in event_graph:
    1. 从 Neo4j 获取事件信息及关联的 StateChange
    2. 分类状态变化：
       - world_fact: 世界事实型（必须应用）
       - potential:  人物内在状态（可选）
       - conditional: 关系状态（可选）
    3. LLM 决策：根据事件内容和当前状态，选择需要应用的状态变化
    4. StateApplier.apply_state_change(): 通过 function calling 应用选中的状态变化
    5. 生成 StateSnapshot（当前完整状态快照）
    6. 记录事件处理结果（含 snapshot、selected_state_changes、decision_point 标记）
```

**状态应用机制**：`StateApplier` 将事件信息、当前状态、候选状态变化打包为提示词，调用 LLM 的 function calling 功能。LLM 根据上下文自主决定调用 `update_character_state()`、`update_relationship_state()`、`update_world_state()` 中的哪些函数，以及传入什么参数。这种设计让 LLM 能够理解事件语义后做出合理的状态更新决策，而非机械地应用所有变化。

**人设动态更新**：在处理剧情转折性事件时，LLM 还可通过 function calling 建议更新角色的静态人设（如角色经历重大事件后世界观发生转变）。

**输入**：Neo4j 事件图谱、状态基线、静态人设

**输出**：`out/canonical_branch.json`（主线记录，含每个事件的状态快照、决策点标记等）

---

## 九、决策点分析

分析主线记录，识别所有决策点和关键事件。决策点是主线中包含多个选择的事件（即原文中存在转折、冲突、选择的情节节点）。系统为每个决策点分析主线选择（canonical_choice）和可能的替代选择方向。

**输入**：`out/canonical_branch.json`

**输出**：`out/decision_points_analysis.json`（决策点列表、关键事件、选择分析）

---

## 十、结局候选确定

系统分析主线和所有可能的支线路径组合，为每个路径确定可能的结局。结局候选池基于原文的可能走向、角色的状态轨迹和叙事逻辑生成。

**输入**：主线记录、决策点分析

**输出**：`out/ending_candidates.json`（所有路径组合和对应的结局候选）

---

## 十一、支线生成

为每个被选中的决策点（分支点）生成替代选择。系统使用 LLM 根据决策点的上下文和当前状态，生成与主线选择不同的替代方案，并为每个替代选择生成对应的状态变化。

支线生成只负责生成分支的基础信息（替代选择描述、初始状态变化），分支后续的事件演化（分支事件链、合流到主线、结局选择）由路径生成阶段处理。

**输入**：主线记录、决策点分析

**输出**：`out/branches.json`（所有分支点的替代选择和初始状态变化）

---

## 十二、路径生成（LangGraph 工作流）

这是系统最核心的技术环节。系统使用 LangGraph 有状态工作流编排所有路径（主线 + 分支路径）的生成。

### 12.1 工作流设计

LangGraph 工作流采用**混合模式**：
- **流程控制**由 LangGraph 图结构管理（节点、边、条件路由）
- **关键决策**由 LLM + function calling 完成（让 LLM 自主判断下一步操作）
- **执行逻辑**由确定性代码完成（状态更新、数据查询等不需要 LLM）

### 12.2 工作流节点

| 节点 | 类型 | 职责 |
|------|------|------|
| initialize | 执行 | 从 branches.json 加载分支点信息，设置初始状态 |
| summarize_history | 执行 | 检查消息历史长度，必要时总结压缩以避免上下文溢出 |
| llm_decision | LLM 决策 | 通过 function calling 让 LLM 决定下一步（三选一） |
| tools | ToolNode | LangGraph 内置的工具执行节点，自动调用 LLM 选择的函数 |
| generate_branch_event | 执行 | 为 LLM 生成的分支事件创建状态变化并应用 |
| process_mainline | 执行 | 合流后处理剩余主线事件，重新生成状态变化 |
| identify_similar_endings | 执行 | 识别候选结局中的相似结局 |
| merge_similar_endings | 执行 | 合并相似结局 |
| select_dramatic_ending | 执行 | 选择文学性最强的结局 |
| create_early_ending | 执行 | 创建分支路径的提前结局 |

### 12.3 LLM 决策机制

`llm_decision` 节点向 LLM 提供三个可调用的工具函数：

1. **generate_branch_event_tool**：生成一个新的分支事件（分支路径尚未合流时使用）
2. **merge_to_mainline_tool**：合流到主线（分支路径的分歧已经展开足够，回归主线）
3. **create_early_ending_tool**：创建提前结局（分支路径走向了无法回归主线的方向）

LLM 根据以下信息做出决策：当前分支的事件历史、已走过的步数、当前状态快照、距离主线的偏离程度。决策后，LangGraph 根据工具调用结果路由到对应的执行节点。

### 12.4 状态一致性保证

分支路径中的每个新事件都经过完整的状态更新流程：
1. `StateChangeGenerator.generate_for_branch_new_event()` 为新事件生成状态变化
2. `StateApplier.apply_state_change()` 通过 function calling 应用状态变化
3. 生成新的 `StateSnapshot`，确保后续决策基于正确的状态

合流后，主线剩余事件也需要基于分支后的新状态**重新生成**状态变化（而非直接复用主线记录的状态变化），以保证状态连贯性。

### 12.5 记忆管理

为防止 LLM 上下文窗口溢出，`summarize_history` 节点在每次决策前检查消息历史长度，超过阈值时使用 LLM 将历史消息压缩为摘要，保留关键信息。

**输入**：主线记录、分支记录、结局候选

**输出**：`out/all_paths/`（每条路径一个 JSON，含完整事件链、状态快照、结局信息）

---

## 十三、路径事件补全

LangGraph 生成的路径可能在某些 fork_event_id 处缺失事件（因为分支路径跳过了该事件）。此阶段扫描每条路径的 events，检查 event_id 的连续性，从 `metadata.path_combination` 中找到对应的 fork_event_id 信息并补上缺失事件，确保路径的事件链完整。

**输入**：`out/all_paths/`

**输出**：`out/all_paths_completed/`（补全后的路径数据）

---

## 十四、内容增强（Content Enhancement）

将路径数据中简短的 `scene_description` 通过 LLM 扩写为文学性的详细场景描述和完整对话。

### 14.1 场景描述扩写

对每个事件调用 LLM，将 `scene_description`（通常为一句话概述）扩展为 `detailed_scene_description`——一段适合文字冒险游戏的叙述性描写。扩写要求：

- **旁白视角**：第三人称叙述（或根据推断的人称），不包含角色直接引语
- **去 AI 味**：注入专用系统预设（`prompts/story_generation_system_prompt.txt`），避免 LLM 常见的冗余修辞
- **上下文感知**：提供前后事件的摘要，确保场景描写的连贯性

### 14.2 对话生成

从事件的 `source_text` 和 `dialogue` 字段中提取或生成完整的角色对话。每条对话包含 `speaker`（说话者）、`text`（台词）、`tone`（语气）。对话生成同样受去 AI 味预设约束。

### 14.3 叙述人称一致性

系统在 `generate-branch` 阶段自动推断原文的叙述人称（第一 / 二 / 三人称），结果写入 `out/content_context.json`。内容增强阶段读取该设定，在所有 LLM 调用中注入人称约束指令，确保全文叙述视角统一。

### 14.4 增量增强

系统支持增量处理：如果某条路径的 JSON 已包含 `detailed_scene_description`（即已被增强过），则跳过该路径，避免重复调用 LLM。

**输入**：`out/all_paths_completed/`（补全后的路径数据）、`out/character_personas.json`（人设，用于对话风格参考）

**输出**：`out/enhanced_paths/`（增强后的路径数据，含详细场景描述和完整对话）

## 十五、Ren'Py 脚本生成

将增强后的路径数据自动转换为 Ren'Py 视觉小说脚本。

### 15.1 角色定义生成（CharacterGenerator）

读取路径数据中出现的所有角色，结合实体表（别名映射），生成 `characters.rpy`。每个角色定义包含：
- 变量名（如 `lin`、`emperor`）
- 显示名称
- 对话颜色
- 立绘关联（`image="var_name"`，从 `sprite_vars.txt` 读取有立绘的角色）

### 15.2 路径脚本生成（PathScriptGenerator）

将每条路径的事件序列转换为 `paths/*.rpy` 脚本。生成规则：

- **场景切换**：根据 `event_scene_map.json`（事件→场景图片映射）自动插入 `scene bg_scene_xx` 语句
- **叙述文本**：将 `detailed_scene_description` 按段落拆分为多条 Ren'Py 旁白语句
- **角色对话**：将 `dialogue` 转换为 `character_var "台词"` 格式，通过实体表统一说话者名称
- **选择菜单**：决策点事件的 `player_choice` 转换为 Ren'Py `menu:` 语法，每个选项 `jump` 到对应路径
- **Flavor 选项**：非决策点事件每隔 N 个事件插入不影响剧情的互动选择（如"继续""沉默片刻"），提升游戏体验
- **content_blocks 支持**：如果事件包含 `content_blocks` 字段，按 blocks 顺序输出（narrative / dialogue / choice 可任意穿插）

### 15.3 结局脚本生成（EndingScriptGenerator）

将每条路径的结局数据转换为 `endings/*.rpy` 脚本，包含结局场景描述、对话和 `return` 语句。

### 15.4 主脚本更新（MainScriptUpdater）

更新 `script.rpy`，生成游戏入口 label 和从主线到各分支路径的跳转逻辑。

**输入**：`out/enhanced_paths/`、`out/entities.json`

**输出**：`wangfo/game/` 下的 `characters.rpy`、`paths/*.rpy`、`endings/*.rpy`、`script.rpy`

## 十六、资源导入与场景映射（import_assets.py）

将第三方美术和音乐资源导入 Ren'Py 游戏工程，并建立事件与场景图片的映射关系。

### 16.1 立绘导入

扫描 `assets/sprites/` 中命名格式为「人名-立绘生成-remove-preview.png」的文件，根据文件名前缀通过 `NAME_TO_VAR` 映射表确定角色变量名，复制为 `game/images/{var}_sprite.png`。自动生成 `images_sprites.rpy`（Ren'Py 图片定义）和 `sprite_vars.txt`（供角色生成器关联立绘）。

### 16.2 场景图片导入

扫描 `assets/scenes/` 中的场景 PNG（命名格式「xxx (n).png」），按序复制为 `bg_scene_01.png`、`bg_scene_02.png` ...，生成 `images_doubao.rpy`。

### 16.3 事件→场景映射

脚本内定义 `EVENT_SCENE_MAP`（事件 ID → 场景图片标签）和 `ENDING_SCENE_MAP`，写入 `event_scene_map.json`，供路径脚本生成器在生成脚本时自动插入 `scene` 语句。

### 16.4 GUI 主题与音乐

从 `assets/Fantasy_project/` 导入 GUI 主题文件，从 `assets/Japanese Music Pack/` 中查找并复制游戏音乐。

## 系统架构总结

本系统采用**"知识图谱构建 → 角色建模 → 状态驱动分支生成 → 内容增强 → 游戏输出"**的五阶段管线设计。核心技术创新在于：

1. **结构化知识约束**：通过事件图谱和角色模型为 LLM 提供结构化的创作约束，避免纯生成式方法的不可控问题
2. **三层状态模型与 Function Calling**：人物内在 / 关系 / 世界三层状态由 LLM 通过 function calling 自主管理，兼顾语义理解能力和状态更新的可控性
3. **LangGraph 工作流编排**：分支路径生成采用有状态的图工作流，LLM 在循环中自主决策，支持检查点恢复和记忆管理
4. **端到端自动化**：从原始文本到可运行游戏的完整自动化管线，23 个步骤通过统一 CLI 编排

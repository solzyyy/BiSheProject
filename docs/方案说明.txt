文字冒险游戏内容生成系统方案说明

一、事件图谱构建

从原始文本中提取结构化事件信息，构建事件知识图谱。通过文本处理将文本分割为段落，利用大语言模型从每个段落中提取事件，包含人物、行动、目标、结果等核心要素。随后分析事件之间的因果关系和时间顺序，生成事件间的关系网络。

输入：原始文本文件

输出：结构化事件列表、事件间关系列表、Neo4j 数据库中的事件节点和关系边

二、人物实体识别与规范化

基于事件图谱，系统识别并规范化文本中出现的所有人物实体。首先提取所有人物提及（Mention），记录每个人物在哪些事件中被提及。随后通过别名识别和指代消歧，将同一人物的不同称呼归并到同一个规范实体下，建立别名映射关系。

输入：事件列表

输出：人物提及表（记录人物在事件中的提及情况）、实体表（包含规范名称和别名映射）

三、状态变化提取

系统从事件图谱中提取三类状态变化：人物内在状态、世界/物品状态和人物关系状态。人物内在状态提取通过定位人物相关事件，分析事件中人物的情绪、动机、世界观等内在维度的变化。世界状态提取直接从事件中识别场景、环境、物品等外部世界的变化。关系状态提取识别事件中人物对之间情感状态、权力动态、连接强度等关系维度的变化。

输入：事件列表、人物提及表（用于定位人物相关事件）、实体表（用于人物别名映射）

输出：人物内在状态变化列表（包含情绪状态、动机、世界观等维度）、世界/物品状态变化列表（包含场景状态、环境状态等维度）、关系状态变化列表（包含情感状态、权力动态等维度）

四、人物画像聚合

系统整合事件数据、状态变化数据和人物提及数据，为每个人物生成完整的动态画像。从事件描述中提取人物的行动词，统计行动频率，并利用 TF-IDF 和 PMI 算法识别每个人物独有的行为模式。最终聚合每个人物的所有相关信息，包括参与的事件数量、行动模式、独有行为、相关的状态变化等。

输入：事件列表、人物内在状态变化、关系状态变化、实体表、人物提及表

输出：人物画像列表（包含行动模式、独有行为、事件统计、状态变化统计等动态信息）

五、静态人设聚合

基于动态的人物画像，系统进一步提取人物的静态人设特征。通过 LLM 分析人物画像中的事件模式、行动模式和状态变化模式，提取五个核心静态属性：叙事角色定位（role）、社会位置（social_position）、性格倾向（disposition）、世界观（worldview）和综合性人设摘要（persona_summary）。

输入：人物画像

输出：静态人设列表（包含 role、social_position、disposition、worldview 和 persona_summary）

六、状态基线初始化

系统扫描所有已提取的状态变化，按目标类型和维度进行聚类，识别出所有可能的状态维度。对于人物内在状态，包括情绪状态、动机、世界观等维度；对于世界状态，包括场景状态、环境状态、物品存在等维度；对于关系状态，包括情感状态、权力动态、连接强度等维度。基于聚类结果，创建状态基线，为每个维度设置初始值。

输入：世界状态变化列表、人物内在状态变化列表、关系状态变化列表

输出：状态基线（包含按目标类型分类的所有维度集合及其初始值，用于运行时状态变量的初始化）

七、数据持久化

系统将实体数据和状态变化数据导入 Neo4j 图数据库，实现数据的持久化存储和高效查询。实体数据作为 Entity 节点存储，状态变化数据作为 StateChange 节点存储，并与事件节点建立关联关系。Neo4j 数据库为状态变化建立了多维索引，支持按目标类型、维度、时间戳等不同维度的快速查询。

输入：实体表、人物状态变化列表、世界状态变化列表、关系状态变化列表

输出：Neo4j 数据库中的 Entity 节点和 StateChange 节点，以及它们与 Event 节点之间的关联关系

八、主线生成

系统从 Neo4j 数据库中的第一个事件开始，逐步遍历所有事件，应用状态变化，生成主线记录（canonical branch）。主线是"无人干预"下真实发生过的历史，不是玩家正在玩的游戏。系统使用 StateApplier 扫描事件知识图谱中与事件节点相连的 StateChange 节点，利用初始化的状态变量，分别更新人物内在状态、人物关系状态和世界/物品状态。状态更新过程利用 LLM 的 function calling 功能，允许 LLM 根据事件内容和当前状态自定义更新逻辑。结合之前得到的静态人设，LLM 可以通过 function calling 判断在剧情比较敏感的事件发生时是否需要更新静态人设。系统识别决策点（包含多个选择的事件）和主线选择（世界真实走了哪条），生成结构化的主线记录，包含事件描述、状态变化、选择的结局等。

输入：事件知识图谱（Neo4j 数据库中的 Event 节点和 StateChange 节点）、状态基线、静态人设列表

输出：主线记录（out/canonical_branch.json，包含所有事件、决策点、状态变化、选择的结局等）

九、决策点分析

系统分析主线记录，识别所有决策点（包含多个选择的事件）和关键事件（最小骨架）。对于每个决策点，系统分析主线选择和替代选择，生成决策点分析结果。决策点分析结果用于后续的支线生成和路径生成。

输入：主线记录（out/canonical_branch.json）

输出：决策点分析（out/decision_points_analysis.json，包含决策点列表、关键事件、选择分析等）

十、结局候选确定

系统分析主线路径和所有可能的支线路径组合，为每个路径组合确定可能的结局。系统生成结局候选列表（包含结局描述、前提条件等）和路径组合列表（包含 path_id、path_combination、candidate_details 等）。结局候选确定结果用于后续的路径生成和结局选择。

输入：主线记录（out/canonical_branch.json）、决策点分析（out/decision_points_analysis.json）

输出：结局候选（out/ending_candidates.json，包含所有路径组合和对应的结局候选）

十一、支线生成

系统基于主线记录和决策点分析，识别所有分支点（被选中作为分支的决策点），为每个分支点生成替代选择。系统使用 LLM 生成替代选择，并生成分支的基础记录（包含替代选择、状态变化等）。支线生成只负责生成分支的基础信息（选择、状态变化），不负责分支的后续演化。分支的后续演化（分支事件链、合流、结局）由路径生成流程处理。

输入：主线记录（out/canonical_branch.json）、决策点分析（out/decision_points_analysis.json）

输出：分支基础记录（out/branches.json，包含所有分支点的替代选择和状态变化）

十二、路径生成（主线+分支）

系统处理所有路径（主线路径和分支路径），生成完整内容。对于主线路径，系统直接使用 canonical_branch.json 的数据。对于分支路径，系统使用 LangGraph 工作流处理分支路径的生成。LangGraph 工作流循环执行以下步骤：

1. LLM 决策节点：LLM 根据当前状态和分支进度，决定下一步操作（生成分支事件 / 合流到主线 / 创建提前结局）
2. 生成分支事件节点：如果 LLM 决定生成分支事件，系统使用 StateChangeGenerator 为分支新生成的事件生成状态变化，然后使用 StateApplier 应用状态变化，更新当前状态
3. 合流到主线节点：如果 LLM 决定合流到主线，系统选择合流点，然后处理合流后的主线事件。对于合流后的主线事件，系统使用 StateChangeGenerator 重新生成状态变化（基于分支后的新状态），然后使用 StateApplier 应用状态变化，更新当前状态
4. 选择结局节点：系统从 ending_candidates.json 中选择匹配的结局

系统将生成的路径格式化为 story_content 或 raw 格式，保存每条路径为独立文件。

输入：主线记录（out/canonical_branch.json）、分支基础记录（out/branches.json）、结局候选（out/ending_candidates.json）、决策点分析（out/decision_points_analysis.json）

输出：路径文件夹（out/all_paths/，每条路径一个 JSON 文件，包含完整的事件链、状态变化、选择的结局等）

系统架构总结

本系统采用模块化设计，分为五个核心模块：核心模块提供基础设施（LLM 调用、文本处理、Neo4j 客户端等），事件图谱模块负责事件图谱构建，人物模块负责人物信息提取和聚合，状态管理模块负责状态应用和快照生成，分支模块负责主线生成、支线生成和路径生成。数据流转形成从原始文本到结构化知识图谱、再到人物画像和静态人设、再到主线记录和分支路径的完整处理链路。系统使用 LangGraph 工作流处理分支路径的生成，支持 LLM 自主决策和状态管理，实现了高度自动化的剧情生成系统。

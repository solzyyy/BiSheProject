## 〇、摘要与关键词

### 中文摘要（300-600 字）

互动叙事游戏因其分支剧情和多结局机制受到玩家青睐，但传统开发方式依赖人工编写大量分支剧本，面临成本高、一致性差、扩展困难等问题。大语言模型虽然具备文本生成能力，但直接用于长篇分支叙事生成时存在状态丢失、角色行为不一致、叙事结构松散等不足。

本文设计并实现了一种基于大语言模型与知识图谱的互动叙事游戏内容自动生成系统。系统以经典文学文本为输入，通过五阶段管线实现从原始文本到可运行视觉小说游戏的端到端自动化生成：（1）事件图谱构建阶段，利用 LLM 从文本中提取结构化事件并构建 Neo4j 知识图谱；（2）角色建模阶段，通过实体消歧、三类状态提取（人物内在 / 人物关系 / 世界物品）和画像聚合建立角色模型；（3）分支路径生成阶段，基于主线记录和决策点分析，使用 LangGraph 有状态工作流编排分支路径，LLM 通过 Function Calling 在工作流循环中自主决策生成分支事件、合流到主线或创建提前结局；（4）内容增强阶段，利用 LLM 将简短场景描述扩写为文学性叙述；（5）游戏输出阶段，自动生成 Ren'Py 视觉小说脚本并导入美术音乐资源。

系统实现了 91 个 Python 源文件共 26,531 行代码，包含 8 套 LLM 提示词模板和 23 个步骤的统一 CLI 管线。以《王佛脱险记》为实验文本，系统成功提取 24 个结构化事件，识别 2 个主要分支点，最终输出包含 23 个 Ren'Py 脚本（4,182 行）的可运行视觉小说游戏。实验结果表明，基于知识图谱约束的生成方式在叙事一致性和角色行为连贯性方面优于直接使用 LLM 生成的方式。

**关键词**：大语言模型，知识图谱，互动叙事，分支路径生成，状态管理，LangGraph，Ren'Py

### English Abstract

This paper designs and implements an automatic content generation system for interactive narrative games based on Large Language Models (LLMs) and Knowledge Graphs. Taking classical literary text as input, the system achieves end-to-end automated generation from raw text to a runnable visual novel game through a five-stage pipeline: event knowledge graph construction, character modeling, branch path generation using LangGraph stateful workflows with LLM Function Calling, content enhancement, and Ren'Py script generation. The system comprises 91 Python source files totaling 26,531 lines of code. Experimental results on "How Wang-Fo Was Saved" demonstrate that knowledge-graph-constrained generation produces more consistent narratives and coherent character behaviors compared to direct LLM generation.

**Keywords**: Large Language Model, Knowledge Graph, Interactive Narrative, Branch Path Generation, State Management, LangGraph, Ren'Py

## 一、前言（选题背景与意义）

### 1.1 选题背景

互动叙事（Interactive Narrative）是数字游戏与人工智能交叉领域的重要研究方向。在互动叙事游戏中，玩家的选择能够影响故事走向，产生不同的分支路径和结局，代表性作品包括《底特律：变人》《巫师 3》等。然而，传统互动叙事游戏的开发面临以下核心问题：

**（1）人工编写成本高**。分支剧本需要编剧手工编写每条路径的对话和场景。一个包含 N 个决策点的故事理论上有 2^N 条路径，分支数量呈指数增长，人工编写成本随之急剧上升。

**（2）跨路径一致性难以保证**。多条分支路径中，角色的性格、关系、世界状态需要保持逻辑一致，但人工维护大量平行状态极易出错。

**（3）扩展性差**。新增一个分支点可能影响后续所有路径，需要大量返工以确保衔接。

近年来，大语言模型（Large Language Model, LLM）的快速发展为自动化叙事生成提供了新的技术可能。GPT-4、Gemini、DeepSeek 等模型展现出强大的文本理解和生成能力。然而，直接使用 LLM 生成长篇分支故事仍存在明显不足：LLM 缺乏显式的状态管理机制，长文本生成中容易遗忘先前设定；不同分支中同一角色可能出现性格矛盾；生成内容缺乏整体规划，容易偏离主题。

### 1.2 选题意义

基于上述背景，本课题提出一种**"知识图谱 + 状态驱动 + LLM 编排"**的技术路线，核心思路是：不让 LLM 凭空创作故事，而是让 LLM 在结构化知识约束下进行有据可依的叙事扩展。

**实用价值**：系统实现了从文学文本到可运行游戏的完整自动化管线，降低了互动叙事游戏的开发门槛，为独立开发者和小型团队提供了可行的内容生成工具。

**学术价值**：系统探索了知识图谱与 LLM 结合的叙事生成框架，验证了三层状态模型与 Function Calling 驱动的状态管理方案在保证长篇叙事一致性方面的有效性。

## 二、综述（相关工作与技术基础）

### 2.1 互动叙事生成系统

互动叙事生成是人工智能领域的经典问题，经历了从规则驱动到数据驱动再到模型驱动的演进：

**规则驱动方法**。Mateas 和 Stern 于 2005 年开发的 Facade 系统是交互式戏剧的先驱，使用基于规则的戏剧管理器（Drama Manager）控制剧情走向。该方法需要设计者预先编写大量规则，扩展性受限。

**AI 角色模拟方法**。Evans 和 Short 于 2013 年开发的 Versu 系统采用基于 AI 的角色模拟，让虚拟角色根据其性格和社交规则自主行动，产生涌现式叙事。该方法适用于社交互动场景，但难以处理复杂的剧情结构。

**LLM 直接生成方法**。2019 年出现的 AI Dungeon 直接使用 GPT-2（后升级为 GPT-3）生成文本冒险游戏内容。该方法的优势在于灵活性和创造性，但存在严重的一致性问题——角色可能突然改变性格，已发生的事件可能被"遗忘"，世界设定可能自相矛盾。

**本系统的定位**。本系统结合了结构化知识表示（知识图谱）与 LLM 的生成能力，通过事件图谱提供叙事骨架，通过三层状态模型维护一致性，通过 LangGraph 工作流编排生成过程，在保持 LLM 创造性的同时解决一致性问题。

### 2.2 关键技术

**（1）大语言模型与 Function Calling**。本系统使用 Gemini 2.5 Pro 和 DeepSeek V3 作为核心推理引擎。Function Calling 是 LLM 的重要能力，允许模型在推理过程中调用预定义的外部函数。本系统利用该机制让 LLM 在理解事件语义后自主决定调用哪些状态更新函数，实现语义理解与程序逻辑的结合。

**（2）知识图谱与 Neo4j**。Neo4j 是原生图数据库，使用属性图模型存储节点和关系。本系统将事件、实体、状态变化建模为图结构，利用 Cypher 查询语言实现高效的关联查询。

**（3）LangGraph 有状态工作流**。LangGraph 是 LangChain 团队推出的工作流编排框架，支持循环执行、条件路由和检查点恢复。本系统使用 LangGraph 编排分支路径生成的循环决策过程。

**（4）Ren'Py 视觉小说引擎**。Ren'Py 是开源的视觉小说引擎，使用自定义脚本语言描述对话、选择和场景切换。本系统自动将生成的叙事内容转换为 Ren'Py 脚本格式。

## 三、方案论证

### 3.1 问题分析

本课题需要解决的核心问题是：如何利用 LLM 从文学文本自动生成多分支、多结局的互动叙事游戏，同时保证跨路径的叙事一致性和角色行为连贯性。

该问题可分解为以下子问题：
- 如何从非结构化文本中提取结构化的叙事元素（事件、角色、关系）
- 如何维护多条分支路径中角色状态和世界状态的一致性
- 如何让 LLM 在约束下自主决策分支路径的走向
- 如何将结构化数据自动转换为可运行的游戏脚本

### 3.2 方案比较

| 方案 | 优点 | 缺点 |
|------|------|------|
| 直接 LLM 生成 | 简单灵活，创造性强 | 无状态管理，一致性差，不可控 |
| 规则引擎 + 模板 | 高度可控，一致性好 | 灵活性差，需要大量规则，创造性不足 |
| **知识图谱 + LLM + 状态管理（本方案）** | 有据可依，一致性好，保留 LLM 创造性 | 实现复杂度高，依赖 LLM API |

### 3.3 本方案设计思路

本系统采用**五阶段管线**架构：

1. **知识图谱构建**：从文学文本中提取事件和关系，构建结构化知识基础
2. **角色建模**：提取人物实体、状态变化和人设特征，建立角色约束
3. **分支路径生成**：基于知识图谱和角色模型，使用 LangGraph 工作流编排 LLM 进行分支决策
4. **内容增强**：利用 LLM 扩写场景描述和对话，提升文学质量
5. **游戏输出**：自动生成 Ren'Py 脚本和导入资源

**创新之处**：
- 提出基于事件知识图谱的结构化叙事约束机制，解决 LLM 生成的不可控问题
- 设计人物内在 / 关系 / 世界三层状态模型，通过 LLM Function Calling 实现语义驱动的状态管理
- 使用 LangGraph 有状态工作流编排分支生成，LLM 在循环中自主决策，支持检查点恢复
- 实现从原始文本到可运行 Ren'Py 游戏的端到端自动化管线

### 4.2 模块划分

系统包含 6 个核心模块，共 91 个 Python 源文件，26,531 行代码。

#### 4.2.1 事件图谱构建模块（src/event_graph）

**功能**：从原始文学文本中提取结构化事件和事件间关系，导入 Neo4j。

**实现方法**：
1. `TextProcessor` 将全文按自然段落分割
2. 对每个段落异步调用 LLM（`AsyncLLMClient.invoke(return_json=True)`），提取事件的 `event_id`、`scene_description`、`source_text`、`dialogue`、`characters` 等字段
3. 对相邻事件对调用 LLM，识别因果（caused_by）和时序（followed_by）关系
4. 通过 `Neo4jClient.upsert_event()` 将事件和关系写入 Neo4j

**数据结构**（Event 节点）：

```json
{
  "event_id": "E5",
  "scene_description": "王佛和林离开宅院，踏上旅途",
  "source_text": "原文对应段落",
  "dialogue": [
    {"speaker": "林", "text": "师父，我们此去何方？", "tone": "恭敬"}
  ],
  "characters": ["王佛", "林"],
  "type": "normal"
}
```

实验数据：从《王佛脱险记》中成功提取 **24 个结构化事件**。

#### 4.2.2 人物模块（src/character）

**功能**：实体识别与消歧、三类状态提取、人物画像聚合、静态人设提取。

**关键算法——行动词 TF-IDF 与 PMI 计算**：

人物画像聚合阶段，系统从事件描述中提取行动词，使用 TF-IDF 和 PMI 识别每个角色的独有行为模式：

- TF-IDF：`tfidf(word, char) = tf(word, char) × log(N / df(word))`，其中 `tf` 为行动词在角色事件中的频率，`df` 为包含该词的角色数，`N` 为总角色数
- PMI：`PMI(word, char) = log₂(P(word, char) / (P(word) × P(char)))`，衡量行动词与角色的共现关联度

**数据结构**（StateChange 节点）：

```json
{
  "event_id": "E5",
  "target_type": "character",
  "target": "林",
  "dimension": "emotional_state",
  "old_value": "平静",
  "new_value": "期待而不安",
  "trigger": "离开宅院踏上未知旅途"
}
```

实验数据：系统识别出 **3 个核心角色人设**（王佛、林、皇帝），提取了人物内在状态、关系状态、世界状态三类变化。

#### 4.2.3 状态管理模块（src/state_manager）

**功能**：维护三层状态模型，通过 LLM Function Calling 应用状态变化，生成状态快照。

**核心设计——LLM Function Calling 驱动的状态更新**：

`StateApplier` 是状态管理的核心类。在处理每个事件时，系统将事件信息、当前状态、候选状态变化打包为提示词，调用 LLM 的 Function Calling 功能。LLM 可调用以下三个函数：

```python
update_character_state(character, dimension, new_value, reasoning)
update_relationship_state(char1, char2, dimension, new_value, reasoning)
update_world_state(dimension, new_value, reasoning)
```

LLM 根据事件语义自主决定调用哪些函数以及传入什么参数。这种设计让 LLM 能够理解事件内容后做出合理的状态更新决策，而非机械地应用所有变化。

**数据结构**（StateSnapshot）：

```json
{
  "character_states": {
    "林": {"emotional_state": "期待而不安", "motivation": "追随师父学画"}
  },
  "relationship_states": {
    "林-王佛": {"connection_strength": "师徒深厚", "trust_level": "高"}
  },
  "world_states": {
    "scene_state": "山间小路", "time_of_day": "清晨"
  }
}
```

#### 4.2.4 分支生成模块（src/branch）

**功能**：主线生成、决策点分析、支线生成、LangGraph 路径编排。

**核心设计——LangGraph 有状态工作流**：

分支路径生成采用 LangGraph 图结构定义的混合模式工作流：

| 节点 | 类型 | 职责 |
|------|------|------|
| initialize | 执行 | 加载分支点信息，设置初始状态 |
| summarize_history | 执行 | 压缩历史消息，防止上下文溢出 |
| llm_decision | LLM 决策 | 通过 Function Calling 决定下一步（三选一） |
| tools | ToolNode | 自动执行 LLM 选择的函数 |
| generate_branch_event | 执行 | 为新分支事件生成并应用状态变化 |
| process_mainline | 执行 | 合流后处理主线剩余事件 |
| select_dramatic_ending | 执行 | 选择文学性最强的结局 |

LLM 在 `llm_decision` 节点通过 Function Calling 从三个工具函数中选择：
- `generate_branch_event_tool`：生成新的分支事件
- `merge_to_mainline_tool`：合流到主线
- `create_early_ending_tool`：创建提前结局

工作流支持检查点恢复（`MemorySaver`），可从中断处继续生成。

**工作流流转图**：

```
initialize → summarize_history → llm_decision
                                      │
                    ┌─────────────────┼─────────────────┐
                    ▼                 ▼                  ▼
             generate_event    merge_mainline      early_ending
                    │                 │                  │
                    ▼                 ▼                  ▼
             summarize_history  select_ending      select_ending
                    │                 │                  │
                    ▼                 ▼                  ▼
             llm_decision          END                END
```

实验数据：系统识别出 **10 个关键事件**、**2 个分支点**，生成多种结局候选，最终输出 **5 条完整故事路径**（1 条主线 + 4 条分支）。

#### 4.2.5 内容增强模块（scripts/content_generator）

**功能**：利用 LLM 将简短的 `scene_description` 扩写为文学性的详细场景描述和完整对话。

**关键设计**：
- 注入去 AI 味系统预设（`prompts/story_generation_system_prompt.txt`），约束 LLM 输出风格
- 自动推断叙述人称（第一/二/三人称），全文保持一致
- 支持增量处理，已增强的路径自动跳过

#### 4.2.6 Ren'Py 脚本生成模块（src/renpy）

**功能**：将增强后的路径数据自动转换为 Ren'Py 脚本。

包含四个生成器：
- `CharacterGenerator`：生成角色定义（`characters.rpy`），自动关联立绘
- `PathScriptGenerator`：生成路径脚本（`paths/*.rpy`），含场景切换、对话、选择菜单
- `EndingScriptGenerator`：生成结局脚本（`endings/*.rpy`）
- `MainScriptUpdater`：更新主脚本入口（`script.rpy`）

路径脚本中自动插入：
- `scene bg_scene_xx` 语句（根据 `event_scene_map.json` 事件→场景映射）
- 角色对话（通过实体表统一说话者名称）
- Flavor 选项（每隔 N 个事件插入不影响剧情的互动选择）

实验数据：生成 **23 个 Ren'Py 脚本文件**，共 **4,182 行**脚本代码。

### 4.3 算法描述

#### 4.3.1 事件提取算法

```
输入：原始文本 T
输出：事件列表 Events, 关系列表 Relations

1. paragraphs = split_to_paragraphs(T)
2. for each paragraph p in paragraphs:
     event = LLM.extract_event(p)     // 异步并发
     Events.append(event)
3. for i in range(len(Events) - 1):
     relation = LLM.extract_relation(Events[i], Events[i+1])
     Relations.append(relation)
4. import_to_neo4j(Events, Relations)
```

#### 4.3.2 主线生成算法

```
输入：Neo4j 事件图谱, 状态基线 S₀, 静态人设 Personas
输出：主线记录 CanonicalBranch

1. state = S₀
2. for each event E in event_graph (按时序):
     state_changes = Neo4j.get_state_changes(E)
     classified = classify(state_changes)  // world_fact / potential / conditional
     selected = LLM.select_changes(E, state, classified)
     (new_state, snapshot) = StateApplier.apply(E, state, selected)  // Function Calling
     CanonicalBranch.record(E, snapshot, selected)
     state = new_state
```

#### 4.3.3 LangGraph 分支路径生成算法

```
输入：主线记录, 分支点 fork_event, 替代选择 branch_choice, 结局候选
输出：完整分支路径（事件链 + 状态快照 + 结局）

1. state = fork_event.snapshot  // 从分支点的状态快照开始
2. loop:
     if len(history) > threshold:
         history = LLM.summarize(history)  // 记忆压缩
     action = LLM.decide(state, history)   // Function Calling 三选一
     switch action:
       case generate_event:
         new_event = LLM.generate(state, context)
         state_changes = StateChangeGenerator.generate(new_event)
         state = StateApplier.apply(new_event, state, state_changes)
         path.append(new_event)
       case merge_to_mainline:
         merge_point = find_merge_point()
         for each remaining mainline event:
           state_changes = regenerate_changes(event, state)  // 基于分支后状态重新生成
           state = StateApplier.apply(event, state, state_changes)
         ending = select_ending(state, candidates)
         break loop
       case create_early_ending:
         ending = LLM.create_ending(state, context)
         break loop
3. return path + ending
```

### 4.4 编程模型与实现技术

**异步并发**：系统大量使用 Python `asyncio` 实现异步 LLM 调用。`AsyncLLMClient` 通过 `asyncio.Semaphore` 控制并发数（默认 5），使用指数退避重试机制（最多 3 次）处理 API 限流和网络错误。

**JSON 容错解析**：LLM 输出的 JSON 可能不完整或包含 Markdown 代码块。`_coerce_json()` 函数实现了多层容错策略：去除代码块标记 → 截取最外层 JSON → 修复截断的字符串值 → 补全缺失的闭合符号。

**统一 CLI**：使用 typer 框架定义 23 个命令，通过 `@app.command()` 装饰器注册。提供交互式菜单（`demo` 命令），按管线顺序引导用户逐步执行。

**实体消歧复用**：Ren'Py 脚本生成阶段复用 `entities.json` 中的别名映射，将对话中的不同称呼（如"皇帝""天子""陛下"）统一为同一角色变量，避免生成重复的角色定义。

## 六、结束语

本文设计并实现了一种基于大语言模型与知识图谱的互动叙事游戏内容自动生成系统。系统的主要贡献包括：

1. **提出了基于事件知识图谱的结构化叙事约束机制**，通过从文学文本中构建事件图谱为 LLM 提供叙事骨架，解决了直接 LLM 生成的不可控问题
2. **设计了三层状态模型与 LLM Function Calling 驱动的状态管理方案**，将人物内在状态、关系状态、世界状态分层管理，通过 Function Calling 让 LLM 自主决策状态更新，兼顾语义理解和程序化可控
3. **使用 LangGraph 有状态工作流编排分支路径生成**，LLM 在循环中通过 Function Calling 自主决策，支持检查点恢复和记忆管理
4. **实现了端到端的自动化管线**，从原始文学文本到可运行 Ren'Py 视觉小说游戏，23 个步骤通过统一 CLI 编排

以《王佛脱险记》为实验文本，系统成功生成了包含 5 条完整故事路径、10 个结局脚本的可运行视觉小说游戏。实验结果初步验证了知识图谱约束方法在叙事一致性方面的有效性。

当前系统仍存在一些局限：LLM API 调用成本较高，完整管线运行时间较长；仅支持单篇文本输入；叙事质量评估缺乏统一标准。未来工作将探索多文本融合输入、本地开源模型部署以降低成本、以及引入玩家反馈的自适应生成策略。
